# PRD 工作流详细 Prompt 模板

> 本文件包含 prd-workflow Skill 各 Phase 的详细 Subagent 调用 prompt 模板。主 Agent 在调用 Subagent 时参考本文件构建 prompt。
>
> **DSH 使用方式**：下面每个模板都只是「本次任务」部分。委派时按 `prd-workflow` 技能里的「Subagent 委派约定」，把 `{repoRoot}/agents/<角色>.md` 的**完整正文放在模板之前**，再用 `subagent` 工具发起委派。模板中出现的 `{knowledgeBase}` 从 `~/.pm-skill/config.yml` 读取；未配置时跳过知识库相关条目。

## Phase 0：需求澄清

主 Agent 直接与用户多轮对话，同时主动查阅知识库获取业务上下文（不调用 Subagent）。

### 知识库辅助

澄清前先读取以下文件建立业务认知：
1. `{knowledgeBase}/CLAUDE.md` — 了解系统全貌（3 应用 7 端）
2. `{knowledgeBase}/index.md` — 定位与需求相关的模块文档
3. 根据用户提到的应用名，读取对应 `名词解释.md` 和相关业务文档

### 澄清问题维度（每轮可提多个问题）

1. **目标**：这个功能要解决什么问题？为什么现在需要？
2. **范围**：涉及哪些端？哪些现有页面需要改动？是否需要新建页面？
3. **用户**：主要面向哪些角色的用户？
4. **优先级**：P0（必须）/ P1（重要）/ P2（一般）？
5. **约束**：有没有技术限制、时间限制、或与其他系统的依赖？
6. **数据**：涉及哪些数据实体？需要新增表还是复用现有表？
7. **权限**：需要新增角色/权限点吗？
8. **支付**：涉及支付流程吗？涉及哪些费用类型？

### context.md 初始化内容

```markdown
# PRD 项目上下文

## 基本信息
- 项目名称：{name}
- 应用：{中台/这里拍/这里查}
- 目标端：{端名}
- 启动日期：{date}
- 优先级：{P0/P1/P2}

## 需求背景
{背景描述，业务现状和痛点}

## 需求目标
{期望达成的目标}

## 影响范围
- 涉及的端：{列表}
- 涉及的模块：{列表}
- 相关知识库文档：{文档路径列表}

## 核心用户故事
| 角色 | 故事 |
|------|------|
| {角色} | 作为{角色}，我希望{功能}，以便{价值} |

## Phase 0 结论
- [ ] 需求范围已确认
- [ ] 涉及端已确认
- [ ] 优先级已确认
```

## Phase 1：需求与设计协作

### pd-agent Prompt 模板

```
你是一位资深产品经理。请完成 Phase 1 的需求分析任务。

【阅读文件】
1. output/context.md — 需求上下文
2. {knowledgeBase}/CLAUDE.md — 系统结构
3. {knowledgeBase}/index.md — 导航索引（找到 {应用名} 章节）
4. {knowledgeBase}/{应用名}/名词解释.md — 术语对齐
5. 知识库中与需求相关的业务文档（通过 index.md 定位）

【任务】
1. 输出功能列表表格：

| 端 | 功能模块 | 页面 | 功能描述 | 优先级 |
|:--:|---------|------|---------|:------:|

2. 为每个功能模块输出核心交互流程：

**功能：[名称]**
- 正常流程：步骤1 → 步骤2 → ...
- 异常流程：异常场景 → 处理方式

3. 标注各端改动点与权限差异（这里拍=运营端/商家端/服务商端/用户端，这里查=运营端/渠道端/用户端）：
- 每个端涉及哪些功能与页面
- 同一功能在各端的权限差异（菜单 / 按钮 / 数据范围）

【输出】
将结果写入 output/prd/phase1-feature-list.md
```

## Phase 2：PRD 初稿

### pd-agent Prompt 模板

```
你是一位资深产品经理。请完成 Phase 2 的 PRD 初稿。

【阅读文件】
1. output/context.md — 全局上下文
2. output/prd/phase1-feature-list.md — Phase 1 功能列表（含交互设计清单）
3. 知识库中所有相关文档

【PRD 结构】（严格按 10 章顺序；结构骨架见 skills/prd-writer/templates/prd-template.md）
一、需求背景
二、需求目标
三、已有功能说明（3.1 现有功能概述 / 3.2 与本次需求的关系）
四、功能范围
五、名词解释
六、用户故事（6.1 用户角色 / 6.2 故事列表）
七、业务流程与业务逻辑（7.1 主流程 / 7.2 分支与异常 / 7.3 核心业务规则 / 7.4 状态流转）
八、功能需求 ⭐ 核心章节
九、非功能需求（只有 9.1 短信与站内信）
十、附录（10.1 相关文档 / 10.2 变更记录 / 10.3 遗留项）

【第八章格式要求 — 最容易出错的部分】
有页面的功能：需求描述 + 核心交互流程 + 页面说明（页面下三段：字段说明 / 校验规则 / 异常处理）。
无独立页面的系统能力：只写需求描述 + 核心交互流程。
字段说明 / 校验规则 / 异常处理**用加粗行，不用 `######` 标题**；**不写原型段**。

【绝对禁止】
- 写「原型链接」「模块影响分析」章节，或写原型段
- 需求描述只写一句话
- 页面内用 `######` 标题写字段说明 / 校验规则 / 异常处理
- 为无页面的系统能力编造「页面 1（无独立页面）」伪页面块
- 出现"交互说明"/"关键交互点"等旧模板废弃段落

【输出】
将 PRD 写入 output/prd/PRD-{功能名称}-v1.md
```

### 初稿自检

PRD 初稿完成后、提交用户确认前，主 Agent 按 `skills/prd-writer/SKILL.md` 的「编写检查清单」逐条核对（10 章齐否、页面内是否残留 `######` 三个分段、是否残留原型段）。

## Phase 3：深度评审

### dev-agent Prompt 模板

```
你是一位资深技术架构师。请对以下 PRD 进行技术可行性评审。

【阅读文件】
1. output/prd/PRD-{name}-v1.md — 待评审 PRD
2. output/context.md — 项目背景
3. {knowledgeBase}/CLAUDE.md — 系统结构
4. 知识库中相关架构文档（权限中心/支付中心/订单中心等）

【评审焦点】
- 「功能范围」章：功能完整性、优先级合理性
- 「业务流程与业务逻辑」章：业务规则可行性、状态流转正确性
- 「功能需求」章：字段类型、校验规则、异常处理
- 「非功能需求」章：短信与站内信触发是否闭环

【输出格式】
1. 评审摘要（综合评分1-5、工作量人天、高风险项数量）
2. 逐项评审（按功能模块，含技术可行性✅/⚠️/❌ + 风险等级P0-P3）
3. 风险清单（风险项/等级/影响范围/缓解方案）
4. 技术方案建议（数据模型/接口设计/权限设计）

将评审报告写入 output/reviews/dev-review.md
```

### qa-agent Prompt 模板

```
你是一位资深 QA 测试工程师。请对以下 PRD 进行测试场景评审。

【阅读文件】
1. output/prd/PRD-{name}-v1.md — 待评审 PRD
2. output/context.md — 项目背景
3. 知识库中相关业务文档

【评审焦点】
- 「业务流程与业务逻辑」章：规则完整性、数据一致性、状态流转
- 「功能需求」章：测试场景覆盖率、逻辑漏洞、边界条件

【输出格式】
1. 评审摘要（覆盖度、问题数、质量风险）
2. PRD 问题清单（分类：[模糊]/[遗漏]/[矛盾]/[不可测]）
3. 测试场景矩阵（每个功能模块：场景/优先级P0-P3/前置条件/操作步骤/预期结果）
4. 验收标准建议
5. 边界条件分析

将评审报告写入 output/reviews/qa-review.md
```

### pd-agent 整合 Prompt 模板

```
你是一位资深产品经理。请整合 DEV 和 QA 的评审意见，修订 PRD。

【阅读文件】
1. output/prd/PRD-{name}-v1.md — PRD 初稿
2. output/reviews/dev-review.md — 技术评审报告
3. output/reviews/qa-review.md — 测试评审报告

【整合原则】
1. 优先级排序：高风险 > 中风险 > 低风险
2. 章节对应：按评审建议修改对应 PRD 章节
3. 最小改动：只修改评审指出的问题
4. 保留原因：在修改处标注评审来源（[DEV] 或 [QA]）

【输出】
1. 整合报告 → output/reviews/integration-report.md
   格式：| 章节 | DEV/QA 建议 | 采纳情况 | 修改内容 |

2. 修订后的 PRD → output/prd/PRD-{name}-v2.md
```

### Phase 3 评审维度引用

tech-review 评审 6 维度（dev-agent 使用）：
1. 数据模型可行性
2. 接口设计合理性
3. 权限体系完备性
4. 跨端一致性
5. 性能与扩展性
6. 安全合规性

test-review 评审框架（qa-agent 使用）：
1. 功能覆盖完整性
2. 边界条件分析
3. 异常场景覆盖
4. 多端兼容性测试
5. 数据一致性验证
6. 用户体验验收标准

## Phase 4：原型交付

### 主 Agent：交互设计清单生成

**映射规则（PRD → 交互清单）：**

| PRD章节 | 提取内容 | 交互清单字段 |
|---------|---------|-------------|
| 第6章 功能需求 - 各端页面描述 | 页面名称、功能列表 | 页面ID、页面名称 |
| 第6章 - 表单字段 | 输入字段、校验规则 | 表单交互（聚焦/失焦/校验反馈） |
| 第6章 - 操作按钮/流程 | 按钮点击、流程跳转 | 点击交互、页面跳转 |
| 第6章 - 列表/表格 | 搜索、筛选、分页、排序 | 列表交互 |
| 第10章 状态流转 | 状态变化触发的UI更新 | 状态交互（禁用/启用/显隐） |
| 第7章 非功能需求 | 加载、空状态、错误处理 | 异常态交互 |

```
从 PRD 的「功能需求」章提取每个页面的交互设计清单，写入 output/prd/interaction-design.md。

生成格式：

# 交互设计清单

## 用户端 - 查询列表页

### 页面基本信息
- 页面ID: user-web-query-list
- 页面类型: 列表页
- 入口: 侧边栏导航"我的查询"

### 交互清单
| # | 交互元素 | 触发动作 | 预期行为 | 异常态 |
|---|---------|---------|---------|--------|
| 1 | 搜索框 | 输入后回车/点击搜索 | 筛选列表数据 | 无结果显示空状态 |
| 2 | 状态筛选 | 下拉选择 | 按状态过滤 | - |
| 3 | "查看详情"按钮 | 点击 | 跳转详情页 | - |
| 4 | 分页器 | 点击页码 | 加载对应页数据 | 加载失败显示重试 |

设计原则：
- 每个页面至少 3 个有意义的交互（不是只有 Toast）
- 多步骤流程必须包含步骤间状态保持和进度指示
- 表单必须包含前端校验（非空、格式、长度）
- 列表页必须包含筛选/搜索/分页的完整交互
- 弹窗/抽屉一律手写（原生 HTML/CSS/JS），必须完整实现关闭、overlay、ESC关闭
```

### ued-agent Prompt 模板

```
你是一位资深 UED 设计师。请根据最终 PRD 和交互设计清单生成高质量 HTML 原型。

【阅读文件】
1. output/prd/PRD-{name}-v2.md — 最终 PRD
2. output/prd/interaction-design.md — 交互设计清单

【生成流程】（严格按两步执行）

Step 1：生成静态布局（按 DDYS 设计令牌手写组件样式）
为每个页面生成完整 HTML 布局，手写组件样式（参照 DESIGN-SPEC.md 规范）：
- 所有字段、表格、表单、按钮、布局结构
- 示例数据（至少 3 行）
- 弹窗、抽屉、Tabs 一律手写（原生 HTML/CSS/JS），参照 v8 原型既有模式
- 每个页面为单文件 HTML，零 CDN 依赖，`:root` 定义 DDYS 设计令牌变量

Step 2：注入业务交互逻辑
基于 interaction-design.md 中的交互清单，为每个页面注入 JS：
- 基础交互（modal/drawer/tabs/toast）用原生 JS 手写实现（含关闭、overlay、ESC关闭）
- 再实现页面特有的业务逻辑（表单联动、实时过滤、计算、多步骤状态）
- 每个交互必须有可见的反馈

【交互质量红线】
- 禁止 showToast('功能开发中') 占位
- 交互组件（modal/drawer/tabs/toast）一律手写（原生 HTML/CSS/JS），但必须达到真实产品交互水准（完整打开/关闭/overlay/ESC 交互）
- 多步骤必须有状态保持（上一步/下一步/进度条）
- 表单必须用原生 JS 校验 + HTML5 validation（非空、格式、长度，含可见错误反馈）
- Tab切换必须手写实现（类切换 + 内容区联动）
- 列表筛选必须实时过滤 Table 行

【端布局类型】
- PC 端管理后台：左侧侧边栏(200px) + 右侧内容区
- 移动端小程序：375px 宽度 + 顶部导航栏 + 全屏内容区
- PC 端宽屏：顶部导航 + 内容区

【输出】
- HTML → output/prototype/pages/{page-name}.html
- 导航首页 → output/prototype/index.html

【验证流程】
1. Bash: npx http-server output/prototype -p 8080 -c-1
2. 验证各页面可正常渲染

【禁止】
- 在对话消息中返回完整 HTML 代码
- 只返回文件路径
```

## Phase 决策矩阵与回退规则

### Phase Decision Matrix（阶段决策矩阵）

| Phase | 启动前置条件 | 完成标志 |
|-------|------------|---------|
| Phase 0 需求澄清 | 用户提出需求意图 | context.md 生成完毕并经用户确认 |
| Phase 1 需求分析 | context.md 已确认 | phase1-feature-list.md + phase1-page-structure.md 生成并经用户确认 |
| Phase 2 PRD初稿 | Phase 1 产出已确认 | PRD 文档按 10 章模板完成、编写检查清单逐条通过，并经用户确认"可进入评审" |
| Phase 3 深度评审 | 用户明确确认"启动评审" | dev-review + qa-review 完成，整合修订后PRD经用户最终确认 |
| Phase 4 原型交付 | PRD最终版确认 | 所有页面原型HTML生成完毕，用户验收通过 |

### 评审启动规则

Phase 2 PRD初稿完成后，**必须由用户明确确认"启动评审"或"进入Phase 3"**，主Agent不得自动触发评审。用户可能在确认前要求小幅调整，这些调整仍属于Phase 2。

### Phase间回退规则

**回退触发条件：**
- Phase 3 → Phase 2：评审报告中 P0 级问题 ≥ 2 个，或存在架构性设计缺陷
- Phase 4 → Phase 2：原型验证中发现 PRD 逻辑错误或重大遗漏
- Phase 4 → Phase 3：原型验证发现非PRD层面的问题（如交互逻辑需要重新评审）

**回退流程：**
1. 主Agent向用户说明回退原因和影响范围
2. 用户确认回退
3. 回退后，从目标Phase重新执行，但仅修订受影响部分（不必重写全部）
4. 修订完成后，需重新走后续Phase（如回退到Phase 2，修订后仍需经过Phase 3评审）
