# PRD 编写规范

## PRD 标准结构（10 章节，严格按顺序）

| 章节 | 名称 | 核心内容 |
|:---:|------|---------|
| 1 | 需求背景 | 业务现状、痛点、为什么做 |
| 2 | 需求目标 | 目标类型 / 目标描述 / 衡量指标 |
| 3 | 已有功能说明 | 与本次需求的关系（不复述存量功能清单） |
| 4 | 功能范围 | 端 / 功能模块 / 页面 / 功能描述 / 优先级 |
| 5 | 名词解释 | 名词 / 定义 / 示例（必须与知识库一致） |
| 6 | 用户故事 | 6.1 用户角色 / 6.2 故事列表 |
| 7 | 业务流程与业务逻辑 | 7.1 主流程（图） / 7.2 分支流程（图） / 7.3 异常流程 / 7.4 核心业务规则 / 7.5 状态流转（图） |
| **8** | **功能需求** | **核心章节，按端 → 主页面组织；下钻并入主页面（见下）** |
| 9 | 非功能需求 | 只保留 9.1 短信与站内信 |
| 10 | 附录 | 10.1 相关文档 / 10.2 变更记录 / 10.3 遗留项 |

> **已移除的章节**（不要再写）：原型链接、模块影响分析。原型不在 PRD 里登记，统一放原型导航页 `output/{project-id}/{iteration-id}/prototype/index.html` 与交付报告。

## 标题编号规则（🔴 必须执行）

| 层级 | 格式 | 示例 |
|------|------|------|
| H2（章） | `## N、名称` | `## 八、功能需求` |
| H3（节） | `### N.M 名称` | `### 7.4 状态流转` |
| H4（功能模块 / 主页面） | `#### N.M.K 名称` | `#### 8.1.3 售后申请` |
| H5（模块内分段） | `##### N.M.K.L 名称` | `##### 8.1.3.1 需求描述` |
| H6（页面 / 下钻） | `###### N.M.K.L.P 名称` | `###### 8.1.3.3.1 发起售后` |

**有页面的功能模块固定三段**：`N.M.K.1 需求描述` → `N.M.K.2 交互说明` → `N.M.K.3 页面说明`。**即使这个模块只有 1 个页面，也必须写出 .3 页面说明 这一层，以及下面的 `````` N.M.K.3.1 页面名，不得省略。** 无页面的系统能力只写前两段。页面内的字段说明 / 校验规则 / 异常处理**不使用标题**，用加粗行 ``字段说明`` 表示。

## 第八章「功能需求」格式（核心，最容易出错）

### 组织单位是「主页面」（🔴 前置）

| 类型 | 判据 | 处理 |
|---|---|---|
| **主页面** | 有独立路由 / 独立入口，用户能停在这页完成一件事 | 一个 ```` 标题（四级标题） |
| **下钻** | 弹窗、区块、从主页面点进去的次级页 | 挂在该模块的「页面说明」下，用 ###### 编号逐条列出，**不提到 #### 同级**；各自拥有独立的字段说明 / 校验规则 / 异常处理三表 |
| **无页面的系统能力** | 规则匹配、状态流转、资金动作、消息通知、操作留痕 | 本章末尾单独一组，标题注明「无独立页面」，只写定位语 + Case |

**反面例子**：① 把「撤销确认弹窗」写成与「售后详情页」同级的标题；② 把页面主体与弹窗的字段打平塞进同一张表、再用「区块」列区分。

**下钻怎么表达**：
- 每个功能模块固定三段：````` N.M.K.1 需求描述 → ````` N.M.K.2 交互说明 → ````` N.M.K.3 页面说明
- 页面说明下按页面逐条列 `````` N.M.K.3.P 页面名，每个页面各自写自己的字段说明 / 校验规则 / 异常处理三张表，**按层级分开、不要合并成一张表**

结构骨架见 templates/prd-template.md，**写 PRD 前必须先读它并按骨架填**。

### Case 的定义（🔴 一个完整业务事件 = 一条 Case）

| 是 Case | 不是 Case（是步骤 / 变体 / 异常） |
|---|---|
| 申请售后、审核工单、撤销申请、创建模板、删除版本、补充材料 | 进入页面、填写诉求、上传附件、点击提交、返回拦截、关闭弹窗、切换 Tab、并发冲突、验证码错误 |

- Case 命名用**动宾短语**，一个事件从「入口」写到「状态变更 + 通知」
- 事件内的分叉写「分支 A／分支 B」，不拆成多个 Case
- 页面状态变体（有工单 / 无工单 / 已终止）写进页面说明
- 异常不占 Case，进异常处理表

### 字段边界（🔴 只写业务数据字段）

字段说明表只写**开发要落库、要传参、要校验的业务数据字段**。以下不属于字段，禁止进表：

- 按钮（提交 / 取消 / 返回 / 上传）
- 展示型计数器（已输入字数、已上传数量、剩余额度）
- 纯提示文案（有效期提示、空态文案）
- 页面标题一类的系统回显

它们写进「核心交互流程」的 Case 步骤里。

### 空表规则（🔴）

校验规则、异常处理两张表**没有内容时整表省略**，连加粗标题一起删。禁止整表只写一行「无」。

### 体量纪律（🔴）

- 单个功能条目（`#### 8.x.x`）建议 **≤ 90 行**；超过 **120 行**必须说明理由（拆功能，或合并同构功能）
- 同一个能力在多端重复出现（如服务商端与商家端一致）时**只写一条**，其余端用「与 8.x.x 完全一致，仅 X 不同」一句引用
- 同一个页面被多个入口共用（如补充材料页、平台介入弹窗）时**只写一条**，入口差异写在 Case 里

### 附录纪律（🔴）

第十章只放「相关文档」「变更记录」「遗留项与前置依赖」。以下属于写作过程产物，**不进 PRD 正文**，另存独立文件：

- 格式自检结果
- 功能条目与章节对照表
- 生成过程说明

## 绝对禁止清单

- 写「原型链接」「模块影响分析」章节
- 写「原型」段或原型预览链接
- 需求描述没有写（一句话不写也不行），或在第八章把第七章的规则完整复述一遍
- 页面内用 `######` 标题写字段说明 / 校验规则 / 异常处理
- **为无独立页面的系统能力编造「页面 1（无独立页面）」伪页面块**
- **把按钮 / 计数器 / 提示文案当字段写进字段说明表**
- **校验规则或异常处理表整表只写「无」**
- **附录里放格式自检、条目对照等写作过程产物**
- 单个功能条目超过 120 行且未合并同构功能
- 出现 "交互说明" / "关键交互点" 等旧模板废弃段落
- 自造业务术语（必须使用知识库中定义的标准术语）
- **字段说明表中将多个字段合并为一行（每个字段必须独占一行）**

## 编写检查清单

- [ ] 10 章节是否齐全且顺序正确（无原型链接、无模块影响分析）
- [ ] 第八章每个功能模块是否**按有无页面**选对了段落组合（有页面才写页面说明）
- [ ] 页面内的字段说明 / 校验规则 / 异常处理是否用加粗行而非 `######` 标题
- [ ] 是否残留「原型」段或原型链接
- [ ] 是否存在「页面 1（无独立页面）」这类伪页面块（有则删）
- [ ] 字段说明表中是否有按钮 / 计数器 / 提示文案混入（有则移出）
- [ ] 校验规则 / 异常处理表是否有整表「无」（有则整表删）
- [ ] 是否存在单条功能超过 120 行、同构功能未合并（有则合并）
- [ ] 附录是否有格式自检 / 条目对照等过程产物（有则移出）
- [ ] 字段说明表中每个字段是否独占一行（禁止合并字段）
- [ ] 名词解释是否与知识库一致
- [ ] 权限需求是否区分菜单/按钮/接口三层
- [ ] 短信与站内信模板是否完整
- [ ] 变更是否已记录到 10.2 变更记录
- [ ] HTML 在线浏览页是否已生成并上传 OSS

## 变更记录规则（🔴 必须执行）

**每次 PRD 变更（新增/删除/修改字段、功能、流程）都必须记录到 PRD 第十章 10.2 变更记录表中。**

### 主记录位置：10.2 变更记录（Markdown表格）

```markdown
| 版本 | 日期 | 修改人 | 修改内容 |
|-----|------|-------|---------|
| v2.0 | 2026-06-06 | PD Agent | [Q25] 变更描述 |
```

### 辅助记录：文件头部 HTML 注释（摘要）

```html
<!-- v[n]变更日志:
[Q25] 变更描述
-->
```

### 注意事项
- 变更编号连续递增（不重置），10.2 和 HTML 注释保持同步
- 描述需具体到字段级别（如"新增单位住所字段"而非"OCR字段调整"）
- 同一次修改涉及多处变更时，每个变更点单独编号
- **10.2 为正式变更记录，必须完整；HTML 注释为摘要，可精简**
- **变更记录按倒序排列**：最新的变更在最前面，最早的（v1.0 初稿）在最后面

## HTML 在线浏览页生成（🔴 必须执行）

**每次 PRD 创建或修改后，必须生成 HTML 在线浏览页并上传 OSS。**

### 生成方式

用本技能自带的渲染脚本（零第三方依赖，输出**单文件 HTML**）：

```bash
# macOS 本机没有系统 node/npm，统一使用 harness 自带 node
$HOME/.dsh/dsh-runtimes/dsh-primary-runtime/dependencies/node/bin/node \
  $REPO/skills/prd-writer/scripts/render_prd_html.mjs \
  <PRD 的 .md 路径> -o <输出 .html 路径> \
  --title "PRD-xxx" --version "v1.5"
```

- 参数：`--title` 缺省取正文第一个 H1；`--version` 渲染到顶部粘性标题栏的版本徽章，**缺省不显示徽章**（版本号取第十章 10.2 变更记录表的最新版本）。
- 脚本把 **marked 源码 + CSS + 页面 JS 全部内联**进单个 HTML，产物**零 CDN、零外部请求**（`grep -E '(src|href)="https?:'` 应为 0）。
- 渲染库固定为 **marked v18.1.0（MIT）**，已本地 vendor 在 `vendor/marked.umd.js`；**不要**改回 CDN 引用，也不要 npm/pnpm 安装依赖，更不要引 mermaid。
- **本机路径替换方式**：换机器时只替换上面两条绝对路径——
  - node：`NODE=$(command -v node || echo ~/.dsh/dsh-runtimes/dsh-primary-runtime/dependencies/node/bin/node)`
  - 脚本：`<本仓库根目录>/skills/prd-writer/scripts/render_prd_html.mjs`
- 输入/输出相对路径按**当前工作目录**解析；脚本渲染后会自检"外部资源引用 = 0 / 内联脚本可安全解析"，不通过则非零退出。

### 图片与原始 HTML 的边界（实测确认）

- **允许**：内联 SVG（团队约定流程图手绘 SVG 内联）、`data:` URI 图片。
- **会被拦下（非零退出）**：`<img src="https://…">` 外链、`<img src="images/a.png">` 相对路径、`<style>@import …</style>`、CSS `url(//…)`。
- ⚠️ **原始 HTML 会穿透**：marked 放行正文里的原始 HTML，所以**不要在 PRD 里粘贴 `<script>`**。浏览页挂在**匿名可读**的 OSS 上。

### HTML 模板要求

- 左侧固定目录导航（H1-H5，滚动高亮）
- 侧边栏整体可收起/展开（✕收起 / ☰展开，带平滑动画）
- 每个 H2 章节支持展开/收起（▼切换，默认展开，滚动时自动展开当前章节）
- 标题样式覆盖 H1-H5（H1=2em/H2=1.5em/H3=1.2em/H4=1.05em/H5=0.95em）
- 顶部粘性标题栏（含版本号徽章）
- Markdown 内容区（表格/代码块/引用块样式优化）
- 回到顶部按钮
- 移动端自适应（隐藏侧边栏）
- OSS 上传路径：`prd/PRD-[名称].html`，Content-Type: `text/html; charset=utf-8`

### OSS 上传

上传动作统一交给 `oss-upload` 技能（零第三方依赖的签名 + `--verify` 上传后校验），**不要再用旧的 `ali-oss` 代码片段**。

- bucket key：`ai-auction-analysis/v1-售前分析/PRD-[名称].html`（前缀按项目，见 `oss-upload` 技能的前缀表）
- Content-Type：`text/html; charset=utf-8`（否则浏览器会下载而不是渲染）
- 凭据由 `oss-upload` **运行时**读取（环境变量或既有脚本），**不要把密钥写进配置文件或本仓库**
- **无凭据时降级**（🔴）：先排查 `credentialsFrom` 指向的既有脚本是否有效；确实取不到时才改用本地 HTTP 服务预览，并在交付说明中注明「**未上传 OSS，交付未完成**」
- 上传通过 `--verify` 后，把**公网链接**回填到**原型导航页与交付报告**；**不要写回 PRD**（PRD 已无原型章节）；本地预览地址不得占用主链接位
